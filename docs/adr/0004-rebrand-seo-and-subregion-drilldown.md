# 品牌改名为「地图记忆」、以静态落地页补 SEO、次区域为第四层下钻

本轮同时做三件事：把站点品牌从「中国行政区记忆」改为「地图记忆」（因为题库早已不止中国行政区，还含 195 个国家）；为纯客户端渲染的 SPA 补上可被爬虫读到的静态落地页；在世界粒度下新增「次区域」层，并把「点地图空白返回上一级」变成通用手势。三者共享同一条约束：**不破坏已上线数据的持久化契约**。

## 改名边界：改用户可见的品牌，不改已持久化的标识

**Status**: accepted

「改名」在本项目有一个硬边界：**凡是已经写进 D1 或 localStorage 的字符串都不改**。具体地，`wrangler.toml` 的 D1 `database_name`（`china-admin-memory-db`）与 19 个 `china-admin-*` localStorage 键前缀保持原样。

理由是 `docs/adr/0001` 已确立的原则：这些字符串是**持久化契约**，不是显示名。其中 `mode-progress:*` 这类键还是**动态拼接**的（含粒度、大洲、次区域 id），重命名意味着一次性迁移所有在线用户的本地进度与云端成绩归属；收益仅仅是「键名好看」，风险是部分用户静默丢数据。**改用户看得见的（标题、品牌、描述、包名、文档），不改数据库认得的。**

`wrangler.toml` 的 `name` 是例外但方向相反：它原本是 `china-admin-memory`，而线上真实 Pages 项目叫 `mapmemorizing`。原值会让 `npm run deploy` **部署到一个陈旧的同名项目**——本地显示成功、线上毫无变化。这不是改名，是**修正一个会导致静默部署错站的错误配置**。

**Considered Options**: ① 连 localStorage 键一起改（配合一次性迁移代码）——迁移代码要读旧键、写新键、删旧键，而 `mode-progress:*` 的键集合是运行时动态展开的，无法可靠枚举，漏一个就丢一段进度；② 连 D1 库名一起改——需新建库 + 导出导入，有丢数据风险却零用户可见收益。均否决。

**Consequences**: 代码里会长期存在「品牌叫地图记忆，但 localStorage 键叫 `china-admin-*`」的观感不一致。这是**刻意保留**的，不要当作历史遗留去「顺手清理」——`src/province.ts:14-20` 与 `functions/_lib/validate.ts:14-27` 的哨兵白名单、以及各 `storageKey()` 方法共同构成契约面，改动即破坏在线数据。

## 次区域是第四层下钻，复用哨兵编码而不新增排行榜表

**Status**: accepted

世界粒度原本只有两层（全世界 → 大洲）。本轮加入「次区域」（东亚、东南亚、西欧、东欧……共 23 个），形成 **全世界 → 大洲 → 次区域** 三级范围，加上中国侧的省级全国 → 单省，整体是四层下钻。次区域**有独立的答题池、独立的进度键、独立的排行榜作用域**，故引入第四个哨兵前缀 `__subregion_<ID>__`，与既有 `__world_nation__` / `__continent_XX__` / `__province_nation__` 并列。

未选「把次区域当作大洲的显示变体、共用大洲榜」：那会让「我在东亚答对 5 国」与「我在全亚洲答对 5 国」记进同一行，用户无法分辨自己的成绩属于哪个范围，而次区域恰恰是本轮新增的主要练习单位。

次区域的划分采用**方位式粗分**（东亚/东南亚/南亚/西亚/中亚…），并明确**没有「北亚」**——俄罗斯整体归入东欧，因为北亚在地理教学与用户直觉中都不是一个独立记忆单元，而俄罗斯跨越欧亚两洲，按方位粗分比按乌拉尔山切分更符合「记住国家位置」这个目标。

**Considered Options**: ① 次区域共用大洲榜——成绩语义混淆，否决；② 新增 `granularity` 列或独立表——需迁移 schema，且与 ADR 0002 否决理由相同；③ 用 ISO 3166 或联合国 M49 官方分区——M49 把哈萨克斯坦等归入「中亚」但把土耳其归入「西亚」的同时把塞浦路斯归入「西亚」，与国内地理教材口径有出入，且分区过多（M49 二级有 22 个，三级更细），不适合「一次记完一个小范围」的目标。

**Consequences**: 引入次区域后，**「国家 → 次区域」映射必须与「次区域 → 大洲」形成严格包含关系**。构建脚本 `scripts/build-subregions.mjs` 用断言强制这一点，并因此**改动了 `countries.json` 里 TUR 与 CYP 的大洲**（两者原为 EU，因归入「西亚」而必须改成 AS）。`scripts/fetch-world-data.mjs` 的 `CONTINENT_OF` 同步修改。若将来重新生成世界数据而不同步这处，断言会失败——这是有意的护栏。

## 以静态落地页补 SEO，而不用 SSR 或预渲染

**Status**: accepted

本站是纯客户端渲染的 SPA：`dist/index.html` 里没有任何地名，蜘蛛（尤其百度）拿到的正文接近零。新增 `scripts/gen-seo-pages.mjs`，在构建时从 `units.json` / `countries.json` / `subregions.json` **生成** 67 个静态 HTML（34 个省级页 + 中国目录 + 世界目录 + 6 个大洲页 + 22 个次区域页 + 404 + robots + sitemap），而不是手写或引入 SSR。

关键点是**这些页面必须与应用内容一致**。脚本因此带六组断言（slug 全覆盖与唯一、大洲国家清单与次区域映射互为反函数、每国恰属一次区域、每省至少有一个真实地级单位、地级总数守恒）。手写 HTML 会随数据变化腐烂，最终变成「落地页说 50 国、应用里 48 国」——这正是搜索引擎判作弊的典型形态。

页面数刻意停在约 60 而非为 373 个地级市各建一页：地级市页面正文只有一行名称，是典型的**薄内容**，批量提交反而拉低整站质量评价。

**Considered Options**: ① 服务端渲染或预渲染框架——为一个无路由的纯前端小站引入构建复杂度，收益与 67 个静态页相同；② 手写落地页——必然与数据脱节；③ 373 个地级市页——薄内容风险。

**Consequences**: 站点内容分布在两处（SPA 与静态页），新增省份/大洲/次区域时必须重新运行生成脚本——已挂进 `npm run build`，故只要走正常构建就不会漏。落地页上的地名通过 URL 参数深链回 SPA（`?g=world&c=AS&s=EAS`、`?g=city&p=440000`），非法参数静默忽略，**不引入客户端路由**。

同时必须存在顶层 `public/404.html`：Cloudflare Pages 在项目没有它时按 SPA 处理，把所有未知路径匹配到 `/` 并返回 **HTTP 200**，于是 `/robots.txt`、`/sitemap.xml` 与任何拼错的 URL 都变成同一页的重复内容，且百度读不到 robots.txt。加上它是安全的：全库 grep 确认**没有任何客户端路由**（零 `pushState`/`history.`/`popstate`/`hashchange`），整个应用只活在 `/`，故不存在被 404.html 破坏的深层链接。

## 站点自定位为「助手」，避免被认定为需版号的网络游戏

**Status**: accepted

站点文案（标题、description、公告、文档）统一使用「记忆助手 / 记忆 / 练习」，**刻意不自称「游戏」**，尽管交互形态是闯关与计分。

原因是版号风险：《网络出版服务管理规定》第二十七条要求网络游戏上线前经审批，而 2009 年新闻出版总署通知的适用范围明文包含**网页游戏、休闲游戏**且**未设商业门槛**；纯免费、无内购并不必然豁免。相反，定位为教育类工具显著降低被归入「网络游戏」的可能，且与实际用途一致。

**Considered Options**: ① 自称游戏以求传播性——引入不必要的监管风险，而用户目标是「更容易被搜到」，游戏类关键词的竞争强度也远高于教育工具类；② 完全不提用途——搜索引擎缺少语义锚点。

**Consequences**: 文案里禁止出现「游戏」作为自我描述（描述他人或泛指场合除外）。若将来确实要按游戏运营，需先解决版号问题，而不是改一句文案。

## 未备案前提下的 SEO 取舍

**Status**: accepted

站点**未完成 ICP 备案**，决定不为此备案。故 SEO 方案只采用不依赖备案的手段：静态落地页、robots.txt、扁平 sitemap、JSON-LD、Open Graph、`noscript` 正文兜底、规范 canonical。

需明示因此**放弃了什么**：百度搜索资源平台的**快速收录**功能以 VIP 俱乐部为前提；**CNAME/DNS 站点验证**自 2023-01-13 起暂停；**自动推送 JS** 与**熊掌号**均已下线；**索引型 sitemap**（sitemap index）被明确拒绝，只能是扁平 urlset。备案**不是**百度任何核心功能的前置条件（百度自身文档把「站点关联主体」与「ICP 备案」并列为两种验证方式，后者更可靠），但未备案确实会损失部分权益与信任信号。

另一个相关判断：**不备案是对的**。本站有留言板，而《互联网电子公告服务管理规定》第二条对「电子公告服务」的定义**逐字包含「留言板」**；腾讯云服务内容目录中，**个人备案**主体可选的只有「博客/个人空间」与「其他」，「网络游戏」不可选。可查的**个人备案被注销**案例（如山西管局 2025-03-10、某站 2025-01-21 注销，理由为「内容与个人备案性质不符」）正属此类冲突。故备案反而会引入一个持续存在的合规风险，而非消除它。

**Considered Options**: ① 为企业/个人备案并保留留言板——存在内容与备案性质不符的实质风险；② 为备案删除留言板——牺牲核心功能换取一个非必需的权益。

**Consequences**: 站点应在 `robots.txt` 与 sitemap 上做得比备案站**更规范**，以弥补缺失的信任信号。同时需人工完成若干**只有站点所有者能做**的验证事项（各搜索引擎站长平台提交站点、验证文件保留永久有效——验证记录会因站点改版而失效）。
